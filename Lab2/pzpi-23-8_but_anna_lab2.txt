2 МОБІЛЬНИЙ ЗАСТОСУНОК
2.1 Мета роботи

     Розробити мобільний застосунок для сучасної платформи (Android або iOS), який є частиною інформаційної системи та забезпечує взаємодію з її серверною частиною. 

2.2  Хід роботи
2.2.1 Опис проєкту

     Назва програмної системи: «Ecofy» 
     Система Ecofy призначена для автоматизації процесів сортування, збору та моніторингу відходів із використанням сучасних інформаційних технологій. Програмний продукт спрямований на підвищення ефективності управління відходами.
     Система передбачає взаємодію декількох категорій користувачів, зокрема побутових користувачів, муніципальних служб, приватних компаній, а також адміністраторів системи. Для забезпечення функціонування системи використовуються серверні технології, база даних, а також інтеграції з IoT-пристроями для моніторингу стану контейнерів.
     У межах даної лабораторної роботи реалізується мобільний застосунок Ecofy для операційної системи Android. 
     
2.2.2 Функціональні вимоги до мобільного застосунку

     FR-1. Авторизація користувача
     Система повинна надавати можливість користувачу авторизуватися у застосунку та зберігати інформацію про поточну сесію.
     FR-2. Реєстрація користувача
     Система повинна забезпечувати реєстрацію нового користувача та створення персонального профілю.
     FR-3. Перегляд статусу контейнерів. 
     Користувач бачить, чи заповнені контейнери, які типи відходів приймаються, та коли очікується вивіз.
     FR-4. Перегляд контейнерних майданчиків на карті
     Система повинна відображати контейнерні майданчики на інтерактивній карті та надавати можливість перегляду детальної інформації про вибраний майданчик.
     FR-5. Отримання сповіщень
     Система повинна повідомляти користувача про час вивозу, оновлення статусу контейнерів, нагадування про роздільний збір. 
     FR-6. Рекомендації щодо сортування відходів
     Користувач повинен мати можливість переглянути підказки щодо правильного сортування різних типів сміття.
     FR-7. Перегляд профілю користувача
     Система повинна відображати основну інформацію про користувача та статистику використання застосунку.
     FR-8. Взаємодія з серверною частиною
     Система повинна отримувати дані про контейнерні майданчики, статус контейнерів, поради та інформацію про користувача через REST API.
     FR-9. Локальне збереження даних
     Система повинна зберігати токен авторизації та вибраний населений пункт у локальному сховищі пристрою для забезпечення автоматичного входу та персоналізації роботи застосунку.

2.2.3 Архітектурні рішення

     Під час розробки мобільного застосунку Ecofy було використано архітектурний шаблон MVVM (Model–View–ViewModel), який забезпечує розділення інтерфейсу користувача, бізнес-логіки та механізмів доступу до даних. 
     Архітектура застосунку складається з таких рівнів:
* Рівень представлення (UI Layer) відповідає за взаємодію з користувачем та містить екрани застосунку (Activity). Завданням рівня є відображення даних та обробка дій користувача.
* Рівень ViewModel (ViewModel Layer) забезпечує підготовку даних для відображення та реалізує бізнес-логіку застосунку. ViewModel отримує інформацію з репозиторіїв, виконує її обробку та передає готові дані до інтерфейсу користувача. 
* Рівень доступу до даних (Repository Layer) реалізує єдину точку доступу до джерел даних. Репозиторії відповідають за отримання інформації із серверної частини системи та локального сховища. 
* Мережевий рівень (Network Layer) реалізований за допомогою бібліотеки Retrofit. Він забезпечує обмін даними між мобільним застосунком і сервером через REST API. Передача даних здійснюється у форматі JSON із використанням протоколу HTTP.
* Рівень локального зберігання даних (Storage Layer) використовує SharedPreferences для збереження токена авторизації та вибраного користувачем населеного пункту. Це дозволяє забезпечити автоматичний вхід до системи та персоналізацію відображуваної інформації.
     Для серверної частини системи використовується фреймворк FastAPI, який забезпечує реалізацію REST API для взаємодії з мобільним застосунком. Зберігання інформації про користувачів, контейнерні майданчики, статуси контейнерів та екологічні поради здійснюється в базі даних PostgreSQL.
     Отримані дані передаються у зворотному напрямку та відображаються користувачу у зручному вигляді. Така архітектура забезпечує масштабованість, підтримуваність та можливість подальшого розвитку функціональних можливостей системи Ecofy.
     Для забезпечення багатомовної підтримки в мобільному застосунку реалізовано механізм локалізації засобами платформи Android. Локалізація виконана шляхом створення окремих ресурсних файлів рядків для кожної підтримуваної мови.
     У проєкті використовуються два файли ресурсів:
* res/values/strings.xml – містить текстові ресурси українською мовою;
* res/values-en/strings.xml – містить відповідні переклади англійською мовою.

2.2.4 UML діаграма прецедентів

     Діаграма прецедентів відображає функціональні можливості мобільного застосунку «Ecofy» та взаємодію користувачів із системою (див. рис. 2.1). 


Рисунок 2.1 – Діаграма прецедентів 
     
     Межі системи – прямокутник, який об'єднує всі прецеденти, показуючи, які саме функції належать до сфери розробки.
     Первинним актором є побутовий користувач, який взаємодіє з такими прецедентами, як реєстрація/авторизація, перегляд станцій сортування, отримання порад щодо сортування, перегляд статусу контейнерів та отримання сповіщень про вивіз сміття.
     Вторинним актором є IoT-пристрій, який забезпечує взаємодію із системою для оновлення та передачі даних щодо стану контейнерів. Це дозволяє користувачу отримувати актуальну інформацію про рівень заповнення та статус сміттєвих контейнерів у реальному часі.
     Діаграма демонструє основні сценарії використання системи та зв’язки між ними, зокрема використання відношень <<include>> та <<extend>> для деталізації поведінки системи.
     
     2.2.2 UML діаграма компонентів
     
     Діаграма компонентів відображає архітектуру мобільної системи Ecofy та взаємодію її основних програмних компонентів (див. рис. 2.2). Центральним елементом діаграми є мобільний застосунок Ecofy Mobile App (Android), який складається з рівня інтерфейсу користувача (UI Layer) та рівня представлення (Presentation Layer), що реалізує логіку взаємодії між інтерфейсом і джерелами даних. Для отримання інформації застосунок використовує Network Layer, побудований на основі клієнта Retrofit, який забезпечує доступ до REST API серверної частини через інтерфейси IAuthAPI, IUsersAPI, INotificationsAPI, IContainersAPI та ITipsAPI. Окремим компонентом є Location Module, який відповідає за роботу з картами та взаємодіє із зовнішнім сервісом Google Maps API.
     Серверна частина представлена компонентом Ecofy Backend API (FastAPI), який реалізує бізнес-логіку системи та забезпечує обробку запитів від мобільного застосунку. Усередині серверної частини виділено функціональні модулі: Auth Module, Users Module, Notifications Module, Containers Module та Tips Module, кожен з яких відповідає за окрему підсистему. Для зберігання даних використовується база даних Azure PostgreSQL, до якої звертаються серверні модулі під час виконання операцій читання та запису.


Рисунок 2.2 – Діаграма компонентів

     На діаграмі прямокутниками позначені програмні компоненти та модулі системи, кружками – інтерфейси взаємодії між компонентами, а стрілками –напрямки залежностей та обміну даними. Пунктирні зв'язки відображають використання інтерфейсів, тоді як суцільні лінії показують безпосередню взаємодію між компонентами системи.

     2.2.3 UML діаграма пакетів
     
     Діаграма пакетів (Package Diagram) є структурним типом UML-діаграм, що відображає організацію системи на рівні логічних групувань компонентів. У даній діаграмі представлено архітектуру Android-застосунку Ecofy, розділену на чотири основні пакети: ui, viewmodel, data (див. рис. 2.3). Пакет ui містить екрани застосунку, згруповані за функціональними модулями (auth, map, notifications, tips, settings), пакет viewmodel – класи для управління станом екранів, пакет data – мережевий шар, репозиторії та моделі даних, а пакет di відповідає за створення залежностей. Стрілки на діаграмі відображають напрямок залежностей між пакетами. 



Рисунок 2.3 – Діаграма пакетів

     Діаграма дозволяє швидко зрозуміти структуру проекту, виявити порушення принципів низького зв'язування та слугує документацією архітектурних рішень застосунку.

2.2.4 Діаграма діяльності

     Діаграма діяльності (Activity Diagram) є поведінковим типом UML-діаграм, що відображає послідовність дій та потік керування в межах певного процесу або функціональності системи. 
     У контексті застосунку Ecofy діаграма описує сценарії взаємодії користувача з додатком, зокрема процеси автентифікації, перегляду карти контейнерів та керування налаштуваннями профілю (див. рис. 2.4). Основними елементами діаграми є початковий та кінцевий вузли, дії (actions), переходи між діями (transitions), умовні розгалуження (decision nodes) та розпаралелення потоків (fork/join), які разом формують повний опис поведінки системи. Діаграма наочно демонструє логіку прийняття рішень, наприклад перевірку токена автентифікації при запуску застосунку або фільтрацію порад за категоріями у модулі tips. 


Рисунок 2.4 – Діаграма діяльності

     Використання діаграми діяльності дозволяє виявити потенційні помилки в логіці застосунку, спростити розуміння складних процесів для команди розробників та слугує основою для написання тестових сценаріїв.

     2.4 Взаємодія з серверною частиною

     Для взаємодії мобільного застосунку із серверною частиною використано бібліотеку Retrofit. У класі RetrofitClient налаштовано базову адресу сервера (https://ecofy-beta.vercel.app/), яка використовується для виконання всіх API-запитів. Для обробки HTTP-запитів використовується клієнт OkHttpClient з підключеним HttpLoggingInterceptor, що дозволяє відстежувати запити та відповіді під час налагодження застосунку. Серіалізація та десеріалізація JSON-даних виконується за допомогою GsonConverterFactory. Через інтерфейс ApiService реалізовано доступ до серверних методів, які забезпечують авторизацію користувачів, отримання інформації про контейнерні майданчики, статуси контейнерів, сповіщення та екологічні поради.
     
      1 package com.example.ecofy.data.network
      2 
      3 import okhttp3.logging.HttpLoggingInterceptor
      4 import okhttp3.OkHttpClient
      5 import retrofit2.Retrofit
      6 import retrofit2.converter.gson.GsonConverterFactory
      7 
      8 object RetrofitClient {
      9
      10    private const val BASE_URL =
      11        "https://ecofy-beta.vercel.app/"
      12
      13    private val logging =
      14        HttpLoggingInterceptor().apply {
      15
      16            level =
      17                HttpLoggingInterceptor.Level.BODY
      18        }
      19
      20    private val client =
      21        OkHttpClient.Builder()
      22            .addInterceptor(logging)
      23            .build()
      24
      25    private val retrofit by lazy {
      26
      27        Retrofit.Builder()
      28            .baseUrl(BASE_URL)
      29            .client(client)
      30            .addConverterFactory(
      31                GsonConverterFactory.create()
      32            )
      33            .build()
      34    }
      35
      36
      37    val api: ApiService by lazy {
      38        retrofit.create(ApiService::class.java)
      39    }
      40
      41
      42 }
      
     Після авторизації користувача сервер генерує токен доступу, який передається мобільному застосунку та зберігається локально за допомогою SharedPreferences. Під час подальших звернень до API цей токен додається до HTTP-запитів для підтвердження особи користувача та контролю доступу до ресурсів системи.
1 class TokenManager(context: Context) {
2
3    private val prefs = context.getSharedPreferences("auth_prefs",    4 Context.MODE_PRIVATE)
5
6    fun saveToken(token: String) {
7        prefs.edit().putString("token", token).apply()
8    }
9
10    fun getToken(): String? {
11        return prefs.getString("token", null)
12    }
13
14    fun saveUserId(userId: Int) {
15        prefs.edit().putInt("user_id", userId).apply()
16    }
17
18    fun getUserId(): Int {
19        return prefs.getInt("user_id", -1)
20    }
21 }
