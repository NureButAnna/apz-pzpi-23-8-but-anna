     3 WEB ЗАСТОСУНОК
     3.1 Мета роботи
     
     Набути практичних навичок проєктування та розробки front-end частини web-застосунку, реалізувати інтерфейси відповідно до ролей системи, забезпечити підтримку інтернаціоналізації та локалізації, а також організувати взаємодію веб-клієнта з серверною частиною системи та засобами адміністрування даних.
     
     3.2 Хід роботи
     3.2.1 Опис прийнятих інженерних рішень
     
     Фронтенд розроблено на React із використанням Vite як засобу збірки. React обрано через компонентний підхід до побудови інтерфейсу, розвинену екосистему бібліотек та широку підтримку спільноти. Vite забезпечує значно швидший час запуску та заміну модулів порівняно зі стандартним Create React App.
     Було реалізовано локалізацію (перемикання між українською та англійською мовами) за допомогою бібліотеки react-i18next із зберіганням обраної мови у localStorage. Усі рядки інтерфейсу винесено до окремих JSON-файлів перекладів, що спрощує подальше додавання нових мов без змін у коді компонентів.
     Фронтенд-застосунок організовано за принципом розмежування відповідальності на рівні каталогів. API-запити винесено до окремих модулів (adminApi, municipalApi, companyApi), що унеможливлює дублювання HTTP-виклику в компонентах та спрощує зміну базового URL або додавання перехоплювачів запитів. Утиліти спільного використання – зокрема функція формування CSV-файлу та хелпер перевірки статусу – розміщені в каталозі utils і підключаються по всьому застосунку без дублювання логіки.
     Компоненти сторінок згруповано за роллю користувача: admin, municipal, company, user. Кожна група містить власні панелі, CSS-модулі та допоміжні компоненти таблиць і бейджів, що мінімізує зв'язність між різними частинами застосунку.
     Готовий проєкт було розгорнуто на хостингу Vercel.
     
     3.2.2 Опис взаємодії компонентів web-застосунку одне з одним та з іншими елементами системи
     
     Веб-застосунок побудований за компонентною архітектурою React. Точкою входу є App.jsx, що визначає маршрути через React Router. Захищені маршрути обгорнуті компонентом PrivateRoute, який перевіряє наявність JWT-токена у localStorage та перенаправляє на відповідний дашборд залежно від ролі користувача, декодованої з токена.
     
      1 const PrivateRoute = ({ children }) => {
      2  const token = localStorage.getItem("token");
      3  return token ? children : <Navigate to="/login" />;
      4 };
      
     Кожен дашборд (AdminDashboard, MunicipalDashboard, CompanyDashboard) складається з компонента Sidebar та основної області відображення активної панелі. Перемикання між панелями відбувається без перезавантаження сторінки через зміну стану active у батьківському компоненті.
     Панелі взаємодіють з бекендом через окремі API-модулі: adminApi, municipalApi, companyApi. При монтуванні компонента useEffect ініціює завантаження даних, які зберігаються у локальному стані через useState. Після мутуючих операцій викликається функція перезавантаження load() для відображення актуального стану.
     
      1 const load = useCallback(() => {
      2  adminApi.getUsers()
      3    .then((r) => setUsers(r.data))
      4    .catch(console.error)
      5    .finally(() => setLoading(false));
      6 }, []);
      7
      8 useEffect(() => { load(); }, [load]);
     Серверна частина реалізована як RESTful API на FastAPI і розгорнута на Vercel. Усі захищені ендпоінти вимагають JWT-токена у заголовку Authorization. Обмін даними відбувається у форматі JSON, виняток – ендпоінт /auth/login, що приймає дані у форматі application/x-www-form-urlencoded згідно зі специфікацією OAuth2. Взаємодія з базою даних PostgreSQL реалізована через SQLAlchemy ORM із сесіями, що автоматично закриваються після обробки запиту.
1 const formData = new URLSearchParams();
2 formData.append("username", email);
3 formData.append("password", password);
4 axios.post(`${API}/auth/login`, formData, {
5    headers: { "Content-Type": "application/x-www-form-urlencoded" },
6 });

     Форми реалізовані як контрольовані компоненти з клієнтською валідацією перед відправкою. Помилки сервера відображаються без перезавантаження сторінки. 
     
     3.2.3 UML діаграма прецедентів
     
     У UML-діаграмі прецедентів для веб-версії системи представлено чотири типи акторів: первинні актори, розміщені зліва, – приватні компанії, муніципальні служби та адміністратор системи, а також вторинний актор, розміщений справа, – IoT-пристрій.
     Система на діаграмі представлена у вигляді прямокутника, який окреслює межі серверної частини програмної системи Ecofy. У межах системи визначено прецеденти або випадки використання (див. рис. 3.1).
     

     Рисунок 3.1 – Діаграма прецедентів

     Таким чином, UML-діаграма прецедентів системи Ecofy відображають повний функціональний набір системи, структуру взаємодії між користувачами, адміністративним персоналом та IoT-пристроями, а також забезпечує розуміння логіки керування процесами збору, обліку та утилізації відходів.
     3.2.4 UML діаграму компонентів (Component Diagram)
     
     Діаграма компонентів (Component Diagram) – це структурна UML-діаграма, яка використовується для відображення архітектури програмної системи, її основних компонентів та взаємозв’язків між ними. Вона демонструє, з яких модулів складається система, які функції вони виконують та яким чином взаємодіють між собою через інтерфейси (див. рис. 3.2).

     Рисунок 3.2 – Діаграма компонентів

     На діаграмі компонентів присутні основні елементи UML-діаграми компонентів:
* Компоненти (Components) – App.jsx, PrivateRoute, Authentication Module, Admin Dashboard, Municipal Dashboard, Company Dashboard, User Dashboard, Shared UI Components, Localization Service, API Services, FastAPI Application. 
* Інтерфейс (Interface) – REST API, через який здійснюється взаємодія між клієнтською та серверною частинами системи. 
* База даних (Database) – Azure PostgreSQL, що використовується для постійного зберігання даних системи, та localStorage для локального зберігання JWT-токена і налаштувань користувача. 
* Хмарний сервіс (Cloud) – Microsoft Azure, у якому розгорнута база даних Azure PostgreSQL. 
* Залежності (Dependencies) – зв'язки між компонентами, що демонструють передачу даних, виклики сервісів та використання функціональності інших компонентів.

     3.2.5 UML діаграму пакетів (Package Diagram);
     
     Діаграма пакетів системи Ecofy є структурною UML-діаграмою, що відображає логічну організацію фронтенд-застосунку через групування модулів у функціональні пакети (див. рис. 3.3). Основними пакетами є pages – з підпакетами для кожної ролі користувача, api – з модулями HTTP-запитів, utils – зі спільними утилітами, i18n – з файлами локалізації. Залежності між пакетами, позначені пунктирними стрілками, відображають відношення імпорту: сторінки залежать від API-модулів, утиліт та компонентів, тоді як точкою входу є App.jsx, що координує маршрутизацію між усіма дашбордами.
     

     Рисунок 3.3 – Діаграма пакетів

     Діаграма допомагає побачити, як саме організований фронтенд на логічному рівні: які модулі згруповані разом, які пакети є незалежними, а які залежать від інших.
     
     3.2.6 UML діаграму діяльності (Activity Diagram)
     
     Діаграма діяльності (Activity Diagram) візуалізує процес використання та ілюструє потік повідомлень від однієї дії до іншої, показуючи цілісну роботу системи. Для візуалізації було обрано всіх акторів системи Ecofy, однак для комунальної служби та адміністратора діаграми не є повними, а демонструють один із можливих сценаріїв – планування вивозів та керування організаціями відповідно (див. рис. 3.4 – 3.7).
     Діаграма звичайного користувача охоплює процес автентифікації, перегляду карти контейнерних майданчиків та порад із сортування відходів. Діаграма компанії-клієнта відображає повний цикл роботи із заявкою – від її створення до отримання фінального статусу (виконано або відхилено), а також перегляд статистики та редагування профілю. 
     Усі діаграми містять обов'язкові елементи, притаманні діаграмі діяльності: початковий вузол (початковий стан системи), дії у вигляді прямокутників зі заокругленими кутами, потоки керування у вигляді стрілок, вузли прийняття рішень, що розгалужують умову на декілька альтернативних варіантів, та кінцевий вузол активності.

     3.5 Висновки
     
     У ході виконання лабораторної роботи було розроблено фронтенд-частину програмної системи Ecofy на основі React і Vite, що реалізує окремі інтерфейси для чотирьох ролей користувачів: звичайного користувача, компанії-клієнта, комунальної служби та адміністратора. Доступ до захищених маршрутів контролюється компонентом PrivateRoute на основі JWT-токена, а перемикання між панелями відбувається без перезавантаження сторінки. Вимогу щодо інтернаціоналізації реалізовано через бібліотеку react-i18next з підтримкою української та англійської мов, а вибір мови зберігається у localStorage. Адміністрування системи забезпечує керування користувачами, організаціями, компаніями, контейнерами та майданчиками, а також експорт даних у форматі CSV з підтримкою кирилиці.
