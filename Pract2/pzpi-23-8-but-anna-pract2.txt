3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про систему
     
     Назва системи: Dropbox
     Розробник: Dropbox Inc.
     Dropbox – це хмарний сервіс для зберігання, синхронізації та спільної роботи з файлами, що дозволяє користувачам отримувати доступ до своїх документів, фото та відео з будь-якого пристрою (ПК, смартфони) через інтернет.
     Програмна система була створена як стартап у 2007 році студентами МІТ Дрю Г'юстоном та Ерешем Фердовзі, отримавши перше фінансування від бізнес-інкубатора Y Combinator.
     Система використовується у різних сферах діяльності:
* особисте використання (зберігання фото, документів, резервне копіювання); 
* освіта (обмін навчальними матеріалами, групові проєкти); 
* бізнес-середовище (спільна робота над файлами, організація документообігу); 
     * ІТ-сфера (зберігання проєктів, обмін кодом та ресурсами).
     Основні функції:
* зберігання файлів у хмарному середовищі; 
* автоматична синхронізація файлів між пристроями; 
* спільний доступ до файлів і папок; 
* історія змін і відновлення попередніх версій; 
* резервне копіювання даних; 
* доступ до файлів з різних платформ (ПК, смартфони, веб-браузер); 
* забезпечення безпеки даних (шифрування, контроль доступу).




     3.2 Архітектурний стиль системи
     
     Dropbox використовує AI-доповнену мікросервісну архітектуру – класична мікросервісна база з подієво-орієнтованою взаємодією через Kafka доповнена окремим шаром генеративного AI, векторного пошуку та LLM-висновку, що реалізований у продуктах Dropbox Dash і Dropbox AI.
     Мікросервісна архітектура обрана через необхідність незалежного масштабування компонентів – під час пікових завантажень File Transfer Service потребує у десятки разів більше ресурсів ніж Auth Service, тоді як монолітна архітектура масштабувалась би цілком. Відмова одного сервісу не зупиняє всю систему, що є критичною вимогою для платформи з 700 мільйонами користувачів. 
     Подієво-орієнтована взаємодія через Kafka забезпечує повну розв'язку між сервісами – після завантаження файлу клієнт отримує відповідь миттєво, тоді як дедуплікація, генерація мініатюр і сповіщення пристроїв виконуються асинхронно у фоні. 
     AI-шар доданий у 2023 році поверх існуючої мікросервісної бази через стандартні API без зміни архітектури – Dropbox Dash реалізує семантичний пошук природною мовою через векторні бази даних і LLM. 
     
     3.3 Основні компоненти системи
     
     Інтерфейс користувача представлений чотирма типами клієнтів: Desktop-застосунок для Windows, macOS і Linux, мобільний клієнт для iOS і Android, вебзастосунок у браузері та інтерфейс Dropbox Dash для AI-пошуку. Кожен клієнт стежить за змінами у файловій системі через системні механізми inotify та FSEvents, підтримує офлайн-режим роботи і автоматично синхронізує зміни після відновлення з'єднання.
     Серверна частина побудована на API Gateway як єдиній точці входу для всіх клієнтських запитів. Load Balancer рівномірно розподіляє трафік між серверами, Auth Service перевіряє токени через OAuth 2.0 і JWT, API Router маршрутизує запити до відповідних сервісів, а Rate Limiter обмежує кількість запитів для захисту від перевантаження. Усі внутрішні сервіси взаємодіють через gRPC і Protobuf за допомогою Envoy Proxy.
     Рівень бізнес-логіки реалізований через незалежні мікросервіси. Sync Engine координує синхронізацію через delta-курсори і виявляє конфлікти. File Transfer Service розбиває файли на блоки по 4 МБ і верифікує кожен блок через SHA-256. Metadata Service зберігає метадані файлів з підтримкою версіонування через MVCC. Deduplication Engine пропускає повторні блоки, Conflict Resolver зберігає обидві версії при конфліктах, Sharing Service керує правами доступу через ACL.
     Рівень зберігання даних розділений на незалежні підсистеми. Magic Pocket – власна розподілена система зберігання блоків у трьох регіональних ЦОД з erasure coding і надійністю 99.9999999999%. Metadata DB на основі MySQL зберігає метадані файлів з атомарними транзакціями. Memcached кешує гарячі метадані для швидкого доступу. Elasticsearch забезпечує повнотекстовий і векторний пошук. Cold Storage зберігає рідко використовувані файли за нижчою вартістю, AWS S3 використовується резервно для 10% даних.
     Допоміжні сервіси забезпечують асинхронну обробку і моніторинг системи. Kafka як шина подій передає події між сервісами – file.uploaded, metadata.changed, sync.conflict. Фонові воркери обробляють події асинхронно: стискають файли, генерують мініатюри і виконують дедуплікацію. Notification Service сповіщає підключені пристрої через WebSocket при змінах файлів. Atlas Platform надає командам автоскейлінг і canary deployments. Prometheus і Grafana забезпечують моніторинг затримки та частоти помилок у реальному часі.





     3.4 Взаємодія компонентів
     
     Діаграма компонентів відображає чотири рівні архітектури Dropbox (див. рис. 3.1): клієнтський рівень, API Gateway (точка входу до системи), основні сервіси, сховище даних та фонові служби.
     

Рисунок 3.1 – Діаграма компонентів

     Діаграма послідовності (рисунок 3.2) відображає покроковий потік завантаження файлу від виявлення змін клієнтом до синхронізації інших пристроїв. Ключовою особливістю є дедуплікація на рівні блоків – якщо SHA-256 хеш блоку вже існує у сховищі, блок не передається повторно, що суттєво економить мережевий трафік і час синхронізації.

Рисунок 3.2 – Діаграма послідовності 

     Отже, завантаження файлу у Dropbox є багатоетапним процесом, де клієнт, сервіси і сховище взаємодіють через чітко визначені протоколи – HTTPS на вході, gRPC всередині системи і WebSocket для сповіщень –  що забезпечує ефективну передачу даних, цілісність блоків і миттєву синхронізацію між усіма пристроями користувача.
     3.5 Масштабованість та надійність
     
     Механізми балансування навантаження:
* Geo-DNS спрямовує користувача до найближчого ЦОД;
* Load Balancer розподіляє запити між серверами, Envoy Proxy – між мікросервісами через gRPC;
* кожен сервіс масштабується незалежно без впливу на інші;
* шардування бази метаданих за user_id рівномірно розподіляє навантаження; 
* Presigned URL дозволяють завантажувати файли напряму у сховище, оминаючи бекенд.
Відмовостійкість:
* Circuit breaker зупиняє несуттєві операції при перевантаженні і запобігає каскадним відмовам;
* Kafka зберігає події при недоступності споживача і обробляє їх після відновлення;
* клієнт працює офлайн через Internal DB – зміни синхронізуються після відновлення з'єднання;
* exponential backoff з jitter захищає від «ефекту грому» при масовому перепідключенні;
* prometheus і Grafana відстежують затримку та помилки у реальному часі.
Кешування:
* memcached кешує метадані перед MySQL – відповідь за одиниці мілісекунд замість десятків;
* CDN кешує файлові блоки біля користувача без звернення до центрального сховища;
* consistent hashing рівномірно розподіляє кеш між вузлами і стійкий до відмови окремих вузлів;

Реплікація:
* Magic Pocket реплікує кожен блок між трьома незалежними ЦОД через erasure coding;
* надійність зберігання – 99.9999999999% при меншому overhead ніж повне копіювання;
* Metadata DB – схема primary-replica з автоматичним failover без втрати даних;
* Kafka реплікує повідомлення між брокерами – жодна подія не втрачається.

     3.6 Приклади програмної реалізації
     
     Опис реалізації мовою програмування Python.
     Назва інструменту та версія: Claude (Sonnet 4.6, Anthropic).
     Внесок автора: самостійний аналіз отриманої інформації, адаптація прикладу під вимоги роботи, оформлення коду та текстових пояснень. 
     Для демонстрації ключових архітектурних принципів Dropbox було розроблено спрощену програмну реалізацію на основі фреймворку FastAPI (Python). Повний текст програми наведено у Додатку В.
     Продемонстровані архітектурні принципи:
* дедуплікація даних. При завантаженні блоку обчислюється його SHA-256 хеш. Якщо такий хеш вже існує у block_store – блок не зберігається повторно, а запит повертає статус «deduplicated»;
* розділення метаданих і даних. Бінарні дані зберігаються у block_store, а службова інформація (ім'я файлу, власник, розмір, список хешів) –  окремо у metadata_db, що дозволяє швидко отримувати метадані без зчитування вмісту файлу;
* блокова структура файлів. Файл розбивається на блоки ChunkInfo, кожен з яких завантажується окремо, а порядок відновлюється через поле chunk_index. Це забезпечує паралельне завантаження та часткове оновлення файлів;
* версіонування. При кожному завантаженні автоматично обчислюється номер ревізії (revision) на основі кількості існуючих записів користувача у metadata_db;
* подієво-орієнтована архітектура. Після кожної операції у чергу event_queue публікується подія, яку фоновий воркер event_worker обробляє асинхронно, імітуючи взаємодію мікросервісів через брокер повідомлень (у реальній системі – Apache Kafka).
